# /quiz — 変更内容の理解度チェック

このブランチで変えたコードを説明できる状態か、4択クイズで確かめる。
AI に書いてもらったコードでも、**中身を分かった上で PR を出す**ための関門。

**これが手順の本体で、Claude Code と Codex の共通仕様。** 片方だけ直さないこと。
**ユーザーが明示的に呼んだときだけ実行する**（Claude Code なら `/quiz`、Codex なら `$quiz`）。自分から勝手に始めない。

合格すると `.git/quiz-pass/<ブランチ名>` にマーカー（合格時の HEAD ハッシュ）が残る。
設定済みの `.agents/githooks/pre-push` が、この clone からの未合格の push を止める。
エージェントも PR 作成前にマーカーの HEAD と点数を確認し、未合格なら PR 作成を保留する。
GitHub のブラウザや API からの PR 作成自体は止められない。

マーカーはツール共通なので、**Claude Code と Codex のどちらで合格しても構わない**。
合格後にコミットを積むとマーカーは無効になり、受け直しになる。

## 実行手順

### 0. clone したリポジトリを確認する

必ずユーザーが clone した対象ディレクトリ内から実行する。スキルの保存場所を作業ディレクトリにしない。
`git rev-parse --show-toplevel` と `git remote get-url origin` で対象を確認し、以後の Git コマンドはそのルートを作業ディレクトリに固定する。
Git リポジトリ外、origin が無い、対象が不明な場合は開始せず、対象の clone の場所をユーザーに確認する。

開始時のブランチ名と `git rev-parse HEAD` を保持する。detached HEAD や、未コミット変更・未追跡ファイルがある場合は
対象を確定できないので開始しない。変更を勝手にコミット・stash・削除せず、先にユーザーと対象を整理する。
クイズの対象はコミット済みの変更であることを伝える。

### 1. 差分を取る

引数にベースが指定されていればそれを使う。

```bash
git diff <指定されたベース>...HEAD
```

指定が無ければ次の順に試す。

1. `gh pr diff` — PR が既にあるなら、レビュー対象と完全に同じ差分で出題できる
2. `git fetch -q origin main` してから `git diff $(git merge-base HEAD origin/main)..HEAD`

`fetch` を省くと古いリモート追跡ブランチとの差分になるので必ず先に取る。
`gh` が利用できない場合は 2 番を使う。fetch が失敗した場合は古い参照で続けない。差分が空なら出題せず終了する。

`gh` が無い場合だけ、クイズの最後に次を一度伝える。

> `gh`（GitHub CLI）を入れると PR の差分をそのまま使えて、より正確に出題できます。
> https://cli.github.com/

### 2. 差分を読む

変更ファイル、追加されたクラス・関数、ロジックの要点、設計判断（どこに責務を置いたか）を掴む。

**このプロジェクト（UE5 / C++ / PvP）で気をつけること**

- **`Content/` は別リポジトリの submodule**。差分はコミットハッシュ 1 行しか出ないので、中身については出題しない。
- **`*.uasset` / `*.umap` は `.gitattributes` で binary 扱い**。diff から意図は読めない。アセットが絡む変更は、`Source/ToonStory/` の C++ と `Config/` の ini を読んで「エディタ上・プレイ中どう変わるか」を掴んでから出題する。読み切れないものは出題対象から外す。
- **`Config/*.ini` は手で入れた行とエディタが勝手に書き足した行が混ざる**（GameFeatures が AssetManager 設定を追記する、など）。意図が読み取れない自動追記は出題しない。
- **Enhanced Input は C++ とアセットにまたがる**。`SetupPlayerInputComponent` / InputAction / IMC（ロール別の割り当て）/ `Config/DefaultInput.ini` の対応関係を確認してから、入力まわりの問題を作る。
- **PvP なのでネットワークが常に効いてくる**。サーバ権威かクライアント予測か、レプリケーション・RPC をどこに置いたかは影響範囲の問いになりやすい。
- `Source/ToonStory/Core|Character|Combat|UI|Data` のどこに置いたかという配置の判断も問いになる。共通処理（`Core/`、GameMode / GameState / PlayerController）に触れた変更は、小さくても影響が広い。呼び出し元を確認してから出す。
- `Binaries/` `Intermediate/` `Saved/` `DerivedDataCache/` `compile_commands.json` は生成物。万一混ざっていても出題しない。
- 複数人で並行して触っているので、「他のメンバーの作業とどうぶつかりうるか」も影響範囲の観点になる。

### 3. 問題を作る

**問題数**（上限 10 問）。ini やアセット追加で行数が膨らむので、**C++ の実質的な変更行**で判断する。

| 実質変更行 | 問題数 |
|---|---|
| 〜50 | 3 |
| 51〜150 | 5 |
| 151〜300 | 7 |
| 301〜 | 10 |

**全問 4 択**。次のカテゴリをバランスよく混ぜる。

- **動作理解** — このコードは何をしているか
- **理由理解** — なぜこの書き方・この置き場所を選んだか
- **影響範囲** — 他のどこに響くか（レプリケーション、他ロール、他メンバーの作業）
- **エッジケース** — 境界条件、初期化順、null / 未設定アセット、通信の遅延や切断時

UE 特有の観点も混ぜてよい。`UPROPERTY` / `UFUNCTION` の指定子の意味、`TObjectPtr` と GC、
`BeginPlay` と `SetupPlayerInputComponent` のどちらに書いたか、`Build.cs` のモジュール依存の追加理由など。

**作問の方針**

- 「何を変えたか」ではなく「なぜ」「どう動くか」を問う
- 誤答は**もっともらしいが明確に間違っている**ものにする
- 4 択を作ってから、**正解の位置を問題ごとにばらす**（A や C に偏らせない）
- 正解は出題時の出力に一切書かない。採点のときに初めて出す

### 4. 出題

1 問ずつ出し、回答を受けてから次に進む。

```
## Q1/5

[問題文]

A) [選択肢A]
B) [選択肢B]
C) [選択肢C]
D) [選択肢D]
```

### 5. 採点

- 正解: 「正解！」とだけ言って次へ
- 不正解: 正解と、該当コードに基づく短い理由を説明する。質問があれば解消してから次へ進む。
- 回答に理由が添えられていて、その理由が間違っている場合も説明する。推測で設計意図を断定しない。

### 6. 結果と合格判定

```
## 結果

正答率: X/Y（Z%）  → 合格 / 不合格

| # | カテゴリ | 結果 |
|---|---|---|
| Q1 | 動作理解 | ✅ |
| Q2 | 理由理解 | ❌ |
```

**合格ライン: 50% 以上（必要正解数は切り上げ）**（3 問なら 2 問、5 問なら 3 問、7 問なら 4 問、10 問なら 5 問）。

記録する前に開始時のブランチ・HEAD と現在値が同じで、作業ツリーが引き続きクリーンか確認する。
異なればマーカーも結果行も発行せず、変更後の内容で受け直す。現在の HEAD を無条件に合格扱いしてはいけない。

合格したときだけ、マーカーを書く。最後の `claude` の部分には、**動かしているツール名**（`claude` か `codex`）を入れる。

```bash
dir="$(git rev-parse --git-dir)/quiz-pass"
mkdir -p "$dir"
printf '%s %s %s %s\n' "$(git rev-parse HEAD)" "$(date +%Y-%m-%dT%H:%M:%S)" "<正解数>/<問題数>" "claude" \
  > "$dir/$(git rev-parse --abbrev-ref HEAD | tr '/' '_')"
```

PowerShell しか使えない環境なら同じ内容を 1 行で書けばよい（形式は `<HEAD> <日時> <正解数>/<問題数> <ツール名>`）。

```powershell
$dir = Join-Path (git rev-parse --git-dir) 'quiz-pass'
New-Item -ItemType Directory -Force $dir | Out-Null
$name = (git rev-parse --abbrev-ref HEAD) -replace '/', '_'
"$(git rev-parse HEAD) $(Get-Date -Format s) <正解数>/<問題数> codex" | Set-Content (Join-Path $dir $name)
```

`.git/` の下なのでコミットされず、clone にも付いていかない。

**あわせて、PR 本文に貼る 1 行を出す。**

```
Quiz: <正解数>/<問題数> @ <HEAD の短縮ハッシュ>
```

短縮ハッシュは `git rev-parse --short=7 HEAD` で取れる。
この行を表示したうえで、**PR を出す導線も案内する**。

> いつもの Git / VS Code で push し、PR 本文に上の結果行を貼ってください。

マーカーはローカルにしか残らない。`.github/workflows/quiz.yml` は PR 作成を事前に拒否するものではなく、
PR が開かれた / 更新されたときにこの自己申告の行を検査する
（head のコミットと一致しているか、50% に届いているか）。コミットを積み直すと行は無効になる。

不合格ならマーカーも結果行も出さず、「もう一度 `/quiz` を実行すれば別の問題で受け直せる」と伝えて終わる。
間違えた点と、復習するコードの場所を短くまとめる。

## 注意事項

- 差分から答えが一意に決まらない問題は出さない
- ファイル名・クラス名を覚えているかだけの暗記問題は出さない
- ユーザーの代わりに回答しない。回答は必ずユーザーから受け取る
- 目的はコードを理解することであって、合格マーカーを作ることではない
