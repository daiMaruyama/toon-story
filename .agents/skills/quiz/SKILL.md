# quiz

ユーザーが明示的に呼んだときだけ実行する（Claude Code は `/quiz`、Codex は `$quiz`）。
回答は必ずユーザー本人から受け取る。エージェントによる代理回答・合格記録の捏造は禁止。

## 1. 対象の確認

- 必ずユーザーが clone した対象ディレクトリ内から実行する。`git rev-parse --show-toplevel` と `git remote get-url origin` で対象を確認し、そのルートで作業する。
- 開始時のブランチと HEAD を保持する。リポジトリ外・対象不明・detached HEAD では開始しない。
- `git status --porcelain` で未コミット変更があれば、先に対象を整理する。勝手に commit・stash・削除しない。

## 2. 出題に必要な差分だけ読む

- ベース指定があれば使う。なければ既存 PR のベースをメタデータで確認し、PR がなければ `origin/main` を使う。
- リモートのベースは一度 fetch し、失敗したら古い参照で続けない。開始時 HEAD とベースの merge-base を固定する。
- まず `git diff --stat <merge-base> <開始時HEAD>` と `git diff --name-status <merge-base> <開始時HEAD>` で全体を把握する。空なら出題しない。
- 重要な動作変更を優先し、`git diff --no-ext-diff --no-textconv --unified=3 <merge-base> <開始時HEAD> -- <必要なパス>` で読む。最初から無制限の全体 diff、全ファイル本文、履歴を出力しない。
- 各ツール出力は目安 3,000 トークン以内。切れた差分は読めた扱いにせず、パスや関数を絞って補う。正解の根拠が足りないときだけ周辺コード・呼び出し元を確認する。
- 会話内ですでに読んだ同じコミットの差分は再利用する。回答のたびに差分・スキルを読み直さない。外部調査やサブエージェントは通常不要。
- 生成物・バイナリ・submodule の中身・意図不明の自動変更は出題しない。UE の権限・RPC・初期化順などは変更に関係するときだけ確認する。
- 重要な変更からの抜粋であり、全変更の理解を保証するものではない。出題対象のファイルを一行で示す。根拠のある3問を作れなければ、その旨を伝え合格記録は発行しない。

## 3. 3問まとめて出す

- 既定は **4択3問**。「どう動くか」「なぜ必要か」「影響・境界条件」を問う。ファイル名の暗記や推測に依存する問題は避ける。
- 問題文は1〜2文、選択肢は各1文まで。誤答は明確に誤りと分かるものにし、正解位置を偏らせない。
- 3問を一度に提示し、`1:A 2:C 3:B` のようにまとめて回答してもらう。正解は回答前に表示しない。ユーザーが希望すれば1問ずつにする。
- 回答が不足・曖昧なら該当分だけ確認する。ユーザーの回答を補完しない。

## 4. 採点と記録

- **50%以上で合格（3問なら2問正解）**。全回答を受け取って採点し、結果は `2/3：合格` のように短く表示する。
- 間違えた問題だけ正解と理由を1〜2文で説明する。詳しい解説は求められたときに行う。結果表や差分の再説明は不要。
- 合格時だけ、開始時と現在のブランチ・HEAD が同じで作業ツリーもクリーンか再確認する。変化があれば記録せず受け直す。
- `git rev-parse --git-dir` 配下の `quiz-pass/<ブランチ名の / を _ に置換>` に、次の形式で1行を保存する。ディレクトリは必要なら作成する。日時は ISO 8601、ツール名は `codex` または `claude`。

```text
<開始時HEADの完全ハッシュ> <日時> <正解数>/3 <ツール名>
```

- 保存成功を確認してから `Quiz: <正解数>/3 @ <開始時HEADの短縮ハッシュ>` を出し、「push後、PR本文にこの行を貼ってください」と案内する。短縮ハッシュは7文字以上。
- 不合格なら記録も PR 用結果行も発行せず、復習する箇所と再実行方法を短く伝える。
- push・PR の制御と制限の範囲はルートの `AGENTS.md` に従う。クイズだけの依頼で push や PR 作成はしない。
